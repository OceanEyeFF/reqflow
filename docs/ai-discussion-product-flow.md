# AI Requirement Discussion Product Flow

## Historical Scope Notice

This document is the MS6 product-flow contract for the initial discussion-to-ticket-draft MVP. Its manual-confirmation invariant remains current, but its exclusions for administrator knowledge-base import, PostgreSQL, pgvector, embeddings, and hybrid retrieval are historical MS6 scope boundaries.

Current operator behavior includes MS7 administrator knowledge-base management, MS9/MS10 PostgreSQL hybrid retrieval, and MS11 AI draft hybrid context/citation/debug evidence. Use `docs/operator-hybrid-search-ai-draft.md` for the current operator runbook.

This document defines the MS6 product flow and information architecture for the Deepseek-backed AI requirement discussion MVP. It is a pre-implementation design contract for WT-20260526-032 through WT-20260526-036.

## Scope Boundary

MS6 delivers a controlled discussion-to-ticket-draft workflow:

- The user describes a vague requirement in a dedicated discussion page.
- The system sends the discussion context and minimal knowledge context to a server-side draft API.
- Deepseek may ask clarification questions before producing a structured ticket draft.
- The user reviews, edits, accepts, or discards the draft.
- Accepted draft content is carried into the existing ticket creation flow.

MS6 does not include:

- Administrator knowledge-base document upload.
- Docs-style zip import.
- Document parsing, chunking, source/version records, or knowledge management UI.
- PostgreSQL, pgvector, vector databases, embeddings, or background indexing.
- Direct client-side Deepseek calls.
- Autonomous ticket creation or mutation.

Those knowledge-base import capabilities belong to `MS-20260527-001 / 管理员项目知识库管理与导入`.

## Existing Ticket Creation Baseline

The current creation surface is `src/app/(dashboard)/tickets/new/page.tsx`. It is a single-page form implementation, not a reusable business form component today.

The current POST endpoint is `src/app/api/tickets/route.ts`.

The current list-page entry to normal ticket creation is `src/app/(dashboard)/tickets/page.tsx`.

The existing create payload contains:

| Field | Current UI source | API behavior | AI draft mapping |
|-------|-------------------|--------------|------------------|
| `title` | required title input | required non-blank string | `draft.title` |
| `description` | optional textarea | saved as nullable text | composed from `background`, `userStory`, `acceptanceCriteria`, `pendingQuestions`, and `citations` |
| `type` | select, default `需求` | must be one of `TICKET_TYPE` values | default `需求`; AI may suggest only existing values |
| `priority` | select, default `medium` | must be one of `low`, `medium`, `high`, `urgent` | `draft.suggestedPriority` |
| `assigneeId` | optional user select | must point to an existing user if present | not generated by AI in MS6 |
| `dueDate` | optional date input | converted to date when present | not generated by AI in MS6 |

Compatibility risks:

- The ticket model has only one `description` field for rich requirement content, so downstream implementation must format structured AI draft sections into readable plain text before handoff.
- `suggestedPriority` must use the existing enum values, not Chinese display labels.
- AI-generated assignee or due date recommendations are out of MS6 scope because they require user/workload policy that does not exist today.
- The current API converts `dueDate` with `new Date(dueDate)` and has no explicit date-format validation; MS6 should not add AI-generated due dates into the handoff payload.
- `citations` are not a database field in MS6; they must be displayed in the draft and folded into the description only after user confirmation.

The least invasive downstream handoff is to prefill the existing new-ticket form after the user accepts the AI draft. This keeps the current ticket creation log, assignment notification behavior, default `pending` status, and post-create navigation owned by the existing `/api/tickets` path.

## Information Architecture

The discussion page should be a work surface, not a marketing entry page.

Primary regions:

1. Discussion composer: raw requirement input, follow-up answers, and user edits.
2. AI clarification panel: visible questions with answer, skip, and regenerate affordances.
3. Draft preview: structured ticket draft with editable sections.
4. Knowledge/citation panel: selected snippets used by the draft and their source labels.
5. Confirmation actions: accept into ticket form, keep editing, discard, or restart.
6. Failure state area: missing configuration, provider timeout, unsafe input warning, empty knowledge fallback, and retry messaging.

The first implementation can keep all discussion state client-side until the user asks the server to generate questions or a draft. No MS6 database migration is required.

## User State Machine

| State | User sees | Allowed actions | Server interaction | Exit condition |
|-------|-----------|-----------------|--------------------|----------------|
| `empty` | Blank discussion composer | enter requirement | none | non-empty input |
| `describing` | Requirement text | edit, submit for AI help | none until submit | user submits |
| `clarifying` | AI questions | answer, skip, ask again | draft API with mode `clarify` | enough context or user forces draft |
| `answering` | Question list plus answer inputs | edit answers, continue | none until continue | user requests draft |
| `generating` | pending draft state | cancel/retry after failure | draft API with mode `draft` | draft or error |
| `draft_ready` | structured draft preview | edit draft, accept, discard, regenerate | optional regenerate call | user chooses next action |
| `handoff_ready` | accepted draft staged for ticket form | open form, return to edit | none | route to ticket form with staged values |
| `ticket_form` | existing new-ticket form with staged fields | final edit, submit, cancel | existing `/api/tickets` only after submit | ticket created or cancelled |
| `failed` | actionable error state | retry, edit, discard | only on retry | successful retry or user exits |

The state machine must enforce this invariant: provider output cannot call `/api/tickets` directly. Only the existing ticket form submission may create the ticket.

## Draft Schema

Downstream code should use an internal provider-neutral contract before adapting Deepseek responses:

```ts
type AiRequirementDraft = {
  title: string;
  background: string;
  userStory: string;
  acceptanceCriteria: string[];
  pendingQuestions: string[];
  suggestedPriority: "low" | "medium" | "high" | "urgent";
  citations: Array<{
    sourceId: string;
    sourceTitle: string;
    snippet: string;
  }>;
};
```

Clarification responses should use a separate contract:

```ts
type AiClarificationResult = {
  questions: Array<{
    id: string;
    question: string;
    reason: string;
  }>;
  canDraftNow: boolean;
};
```

The draft endpoint may return either clarification questions or a draft, but the UI should keep those states distinct so the user understands whether they are still discussing or reviewing a draft.

## Description Formatting

When the user accepts the draft, the existing `description` textarea should receive a deterministic plain-text composition:

```text
背景
<background>

用户故事
<userStory>

验收标准
1. <criterion>
2. <criterion>

待确认问题
1. <question>

引用片段
- <sourceTitle>: <snippet>
```

The formatter must omit empty optional sections and must not hide unresolved pending questions.

## Deepseek Boundary

WT-031 does not implement Deepseek calls. The product/API boundary for later worktracks is:

- Browser calls only an internal ReqFlow API endpoint.
- The internal endpoint performs auth checks, input validation, redaction, timeout, rate/cost guard, knowledge context assembly, and provider invocation.
- Deepseek API key, base URL, model, timeout, and retry policy remain server-side configuration.
- Provider response is normalized into `AiClarificationResult` or `AiRequirementDraft` before reaching UI code.
- UI never depends on Deepseek-specific response shapes.

The later implementation worktrack must re-check official DeepSeek documentation before coding endpoint, model, authentication, streaming, timeout, and error behavior.

## Knowledge Context And Citations

MS6 uses minimal inspectable context:

- tracked repository documents approved by WT-032;
- small source-controlled snippets approved by WT-032;
- current discussion text and user answers.

Citation rules:

- Every citation must include a source title and short snippet.
- The draft can still be generated when no knowledge snippet is available, but the UI must show an empty-knowledge fallback.
- Citations are advisory context, not proof that the final requirement is correct.
- Uploaded administrator documents and docs zip imports are excluded until MS7.

## Manual Confirmation Invariant

The AI workflow has three separate boundaries:

1. Generate: provider returns questions or a draft.
2. Stage: user accepts the draft into editable ticket-form fields.
3. Create: user submits the existing ticket form.

Only step 3 can call `/api/tickets`.

Required UI/API safeguards:

- No provider response handler may POST directly to `/api/tickets`.
- The accept action stages values; it does not create a ticket.
- The final ticket form remains editable before submit.
- Discard removes staged AI output without side effects.
- Existing ticket audit behavior starts only after user-confirmed ticket creation.

## Failure States

The MVP must design for:

- unauthenticated user: redirect or 401 from internal API;
- empty or too-short requirement: local validation;
- missing `DEEPSEEK_API_KEY`: server error with operator-safe message;
- provider timeout or rate limit: retry affordance without losing user text;
- unsafe or sensitive input warning: ask user to remove secrets before sending;
- empty knowledge context: generate without citations and disclose that no snippets were used;
- malformed provider output: show failure and keep current discussion state.
