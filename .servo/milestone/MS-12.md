## Purpose

把现有 AI 追问从普通澄清升级为面向业务流程审查的 Business Interrogation：在生成草稿前显式识别知识库覆盖缺口、流程矛盾、例外规则、角色责任边界、状态流转、异常分支和验收风险，并把这些问题按阻塞程度展示给用户。

该 milestone 的目标不是单纯增加 prompt 文案，而是建立一个可验证的追问质量闭环：检索覆盖诊断 -> evidence-aware provider 输入 -> 分级问题 schema -> 前端分组展示 -> golden case 验收。

## Scope Boundary

- 不自动创建工单，不改变 AI 草稿人工确认边界。
- 不把知识库全文或无界上下文发送给 provider。
- 不把缺失知识库覆盖伪装成已有依据；当核心术语没有命中时必须暴露 coverage gap。
- 不把 BM25/pg_search 写成当前默认事实；MS-12 只做 BM25 readiness/design 与检索抽象准备，除非目标环境和 runtime bundle 已验证可用。
- 不把本地 embedding sidecar 变成默认生产路径；真实索引链路必须经过单独 Worktrack 验收。
- 不引入外部托管搜索服务、第三方向量数据库或外部 reranker 作为必须路径，除非 fdch0 单独确认。

## Design Decisions To Carry Forward

1. Clarify mode must receive safe retrieval evidence, including matched terms, missing core terms, citation count, vector lane status, active lexical engine, and selected knowledge-base scope.
2. Question output must include at least category, priority, blocksDraft, basis, reason, relatedText, and expectedAnswerFormat.
3. Question categories should cover coverage_gap, exception_rule, actor_boundary, state_flow, failure_path, data_rule, acceptance_risk, and knowledge_conflict.
4. Frontend should group questions by business impact: blocking questions, recommended questions, and knowledge-base gaps.
5. Empty or weak retrieval is not a provider failure by itself; it is a first-class diagnostic state that should produce coverage-gap questions.
6. BM25 work in MS-12 is readiness and abstraction work only. Runtime enablement depends on a Docker/runtime environment that can install and verify pg_search safely.

## Completion Signals

1. AI clarify requests include safe search/coverage evidence rather than only final citations.
2. The provider can ask high-value business-analysis questions when the knowledge base has no direct coverage.
3. The question schema distinguishes blocker questions from optional clarifications.
4. The UI shows knowledge gaps and blocking questions without hiding retrieval weakness.
5. Golden case "一般耗材标准检验出库" produces questions about knowledge coverage, exception rules, direct-outbound boundary, QC sampling quantity, QC抽样 vs QC取样, failure path, and inner/outer warehouse responsibility.
6. BM25/pg_search readiness, fallback, and lexical engine abstraction boundaries are documented without claiming unavailable behavior.
7. Optional local embedding sidecar indexing path is validated or explicitly deferred with evidence.

## Acceptance Criteria

1. Focused tests cover coverage diagnostics, empty-hit behavior, safe evidence serialization, and provider request shape.
2. Clarify output tests cover question categories, priority, blocksDraft, basis, and fallback behavior.
3. Frontend tests or equivalent local validation prove grouped question rendering and answer preservation.
4. Golden case evaluation records expected high-value questions and fails if only generic questions are produced.
5. `npm run lint`, `npm run test`, `npm run build`, PostgreSQL readiness, search extension readiness, and retrieval evaluation pass or have explicit not-applicable evidence.
6. No provider secret, raw API key, disabled knowledge content, or unauthorized knowledge-base content is exposed in search evidence or UI.

## Milestone Gate Design

- black_box: 用户输入复杂中文业务流程时，系统能先指出知识库覆盖缺口和关键业务风险，再生成或阻止生成草稿。
- white_box: coverage diagnostics、safe search evidence、provider prompt、question schema、UI grouping、golden case harness 和 fallback path 均有测试或验收证据。
- anti_cheat: 不允许靠泛问题冒充高质量追问；不允许把无命中说成有依据；不允许绕过人工确认；不允许把 unavailable BM25 或未索引 embedding sidecar 写成已启用能力。

## Developer Decision Boundary

- 启用 pg_search/BM25 作为默认 runtime、引入外部 reranker、改变 provider 成本边界、生产化本地 embedding sidecar、或批量重建生产知识库 embeddings 需要 fdch0 单独确认。
