## Purpose

在 MS-9 建立的 PostgreSQL 与 extension 基线之上，实现知识库 hybrid retrieval：query understanding、lexical BM25/FTS 召回、embedding + pgvector 语义召回、RRF 融合排序、权限过滤、Context Window Builder、相邻 chunk/文件级上下文扩展，以及可解释 score/citation/debug evidence 输出。

## Scope Boundary

- 以 PostgreSQL 为目标数据库。
- 优先使用 MS-9 确认的 BM25 方案；若不可用，使用 MS-9 确认的 FTS fallback。
- embedding 生成必须受 provider secret/server boundary 保护，并可在测试中使用 deterministic fake。
- embedding 生成必须绑定 active SearchIndexProfile；同一检索只比较同一 profile 内的 vectors。
- 检索必须始终遵守 knowledge base enabled/archived、source enabled/status、snippet enabled 和用户选择范围。
- provider context 必须有上限，不允许发送整库或整包原始文件。
- Lexical、vector 和 fusion 分数必须保留可审查 evidence；不同打分体系不得直接 raw score 相加。
- 可预留 reranker seam，但不得在没有质量 gate 和成本/隐私边界时引入外部 reranking provider 作为必须路径。

## Implementation Architecture Notes

1. Provider abstractions should remain explicit: `EmbeddingProvider`, `LexicalSearchEngine`, `VectorSearchEngine`, `HybridRetriever`, and context builder responsibilities should not be conflated.
2. Query understanding should produce separate lexical and embedding inputs so Chinese normalization, domain terms, and semantic expansion can evolve independently.
3. Structured metadata should be indexed alongside snippet text and source/version provenance, not treated as AI-only enrichment.
4. Context Window Builder should merge adjacent chunks, deduplicate overlapping snippets, group by citation/source, enforce token/character caps, and preserve provenance for every included span.
5. Debug evidence should be available to tests and an admin/debug surface: lexical hits, vector hits, fused rank, filtered reasons, final context membership, and score breakdown.
6. pgvector search should account for filter-first behavior and recall loss under narrow knowledge-base/source/profile filters by testing larger candidate pools and index strategies.

## Completion Signals

1. 知识片段具备可检索 index schema，支持 lexical 与 vector 双路召回。
2. KnowledgeEmbedding 记录 profileId、model、dimensions、contentHash 和状态；换模型或维度不会静默复用旧向量。
3. 中文业务查询能通过 lexical/vector/fusion 命中相关知识，而不是依赖简单 includes。
4. 检索输出包含可审查的 score breakdown 或 debug evidence。
5. 禁用/归档知识库、禁用 source/snippet、未选择知识库均不会被召回。
6. 命中结果能扩展相邻 chunk 或文件级上下文，并保留 source/path/section/snippet citation。
7. Evaluation harness 能用固定中文业务样例验证 lexical-only、vector-only、fusion、filter 和 context builder 输出。

## Acceptance Criteria

1. Hybrid retrieval 测试覆盖 lexical-only、vector-only、RRF fusion、误召回、forbidden source、权限过滤和 context cap。
2. embedding provider 失败时有可控降级，不破坏 lexical 检索。
3. active SearchIndexProfile 缺失、building、deprecated 或 dimensions mismatch 时，vector retrieval 不得静默运行。
4. 上下文扩展有大小上限并可测试。
5. 不伪造 citation，不返回未命中的 source 作为证据。
6. Debug evidence 能解释最终结果来自 lexical、vector、fusion、metadata filter 或 context expansion 的哪一步。
7. `npm run lint`、`npm run test`、`npm run build` 和 PostgreSQL DB readiness 通过。

## Milestone Gate Design

- black_box: 用户输入中文业务问题时，系统稳定召回相关知识片段并显示可追溯引用。
- white_box: BM25/FTS、pgvector、SearchIndexProfile、embedding status、query understanding、RRF fusion、filter、context builder、debug evidence 均有测试证据。
- anti_cheat: 不允许整库塞给 AI；不允许绕过过滤；不允许只靠 vector 隐藏 lexical 漏召回；不允许不可解释排序；不允许混排不同 SearchIndexProfile 的 vectors。

## Developer Decision Boundary

- 变更 embedding provider 计费策略、引入后台批处理队列、使用外部搜索服务或批量重建生产知识库需要 fdch0 单独确认。
