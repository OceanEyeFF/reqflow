## Purpose

Decide whether ReqFlow should keep the current PostgreSQL/pgvector runtime
without BM25 as the default, keep ParadeDB as an optional candidate profile, or
move toward ParadeDB `pg_search` as the default PostgreSQL runtime while the
product is still pre-production.

The milestone must estimate cost, expected benefit, residual risk, and follow-up
implementation scope for each path before any runtime switch is made.

## Scope Boundary

- Compare three paths:
  1. keep current non-BM25 PostgreSQL default runtime;
  2. keep ParadeDB as optional profile/candidate runtime;
  3. move toward ParadeDB as default runtime.
- Use MS-13, MS-14, and MS-15 evidence as primary source.
- Estimate engineering cost, validation cost, migration cost, rollback cost,
  operator cost, developer experience impact, and product/search benefit.
- Treat pre-production status as a cost/risk modifier.
- Produce a decision gate and follow-up implementation plan.
- Do not change `docker-compose.runtime.yml` in this milestone.
- Do not migrate or delete Docker volumes, uploads, model cache, or database state.
- Do not implement app retrieval changes in this milestone.
- Do not claim BM25 is active in the default runtime.

## Design Decisions To Carry Forward

1. MS-15 accepted ParadeDB `pg_search` as a validated candidate runtime, not as
   an active default runtime.
2. Current default remains PostgreSQL/pgvector plus native FTS fallback.
3. Because the product is not yet in production, default-runtime switch cost is
   lower than it would be after launch, but still must be explicitly estimated.
4. Any actual switch requires a later implementation worktrack or milestone.
5. App retrieval integration must preserve RRF-style fusion and avoid raw score
   addition.
6. `pdb.unicode default` is ranking-compatible on the current benchmark corpus
   but not final proof of word-level Chinese segmentation.

## Completion Signals

1. A cost/benefit/risk scoring model exists for all three paths.
2. ParadeDB default-runtime migration and rollback costs are explicitly
   estimated.
3. App retrieval integration scope and product benefit are explicitly estimated.
4. The final ADR recommends keep / optionalize / switch and states confidence.
5. Follow-up implementation Worktracks are defined if the recommendation is
   ParadeDB default runtime.
6. fdch0 decision boundary is preserved.

## Acceptance Criteria

1. Cost estimates include engineering, validation, migration, rollback,
   operations, and developer experience dimensions.
2. Expected benefits include search quality, Chinese compatibility, product
   capability, and simplification/complexity tradeoffs.
3. Risks distinguish pre-production acceptable risks from production blockers.
4. Recommendation does not rely on raw-score comparison across retrieval lanes.
5. Final report does not claim BM25 active behavior unless a later default
   runtime switch is separately implemented and approved.
6. `npm run lint`, `npm run test`, and `npm run build` pass or are explicitly
   not applicable with reason.

## Milestone Gate Design

- black_box: reader can choose among three runtime paths using explicit cost,
  benefit, and risk estimates.
- white_box: the recommendation traces back to MS-13/MS-14/MS-15 evidence and
  names the missing implementation/validation steps.
- anti_cheat: do not treat pre-production as a reason to skip rollback analysis;
  do not hide migration cost; do not claim BM25 active by recommendation alone;
  do not collapse optional profile and default runtime into the same decision.

## Developer Decision Boundary

- fdch0 must make the final runtime selection decision.
- Any default runtime switch, existing volume migration, production deployment
  choice, or app retrieval implementation remains out of scope until a later
  approved Worktrack or Milestone.
