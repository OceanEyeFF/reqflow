## Purpose

让非专业用户在 discussion 页面输入模糊需求、补充上下文并回答 AI 追问后，由 Deepseek 生成结构化、可审查的工单草稿；AI 只辅助起草，必须由用户人工确认后才带入现有工单表单或创建流程。本 milestone 使用 repo 内稳定资料或少量内置语料作为最小知识上下文，不实现管理员知识库上传/zip 导入，不依赖 PostgreSQL/pgvector。

## Completion Signals

1. Discussion 产品流定义清楚：初始描述、AI 追问、用户补充、草稿生成、人工确认和失败态明确。
2. 最小知识上下文来自 repo 内稳定资料和少量内置语料，并能在草稿中展示引用片段；管理员上传和 zip 导入延后到 MS7。
3. 后端提供受鉴权保护的 Deepseek draft API/provider adapter，输入 discussion 上下文，输出结构化草稿。
4. 前端提供 AI 需求生成 discussion 页面，生成结果只进入草稿/表单确认流，不直接创建工单。
5. 安全治理覆盖 Deepseek secret、prompt 边界、敏感信息提示、错误处理、限流/超时、空知识 fallback、人工确认约束。
6. API 基础测试、弱输入/正常输入路径、discussion 页面手动验收路径通过。

## Acceptance Criteria

1. 用户能在 discussion 页面输入一段非专业需求，经过 AI 追问/补充后得到结构化工单草稿。
2. 输出至少包含标题、背景、用户故事、验收标准、待确认问题、建议优先级和引用片段。
3. AI 不直接创建工单，必须人工确认后才带入或提交到现有工单流程。
4. Deepseek 调用只发生在服务端，API key、base URL、模型、超时和限流均为服务端配置。
5. 不引入 PostgreSQL/pgvector 依赖，不实现管理员知识库上传/zip 导入。
6. 不破坏现有工单创建流程。
7. `npm run lint`、`npm run test`、`npm run build` 通过，或 Gate 记录等价验证理由。

## Milestone Gate Design

- black_box: 用户可从 discussion 页面输入非专业需求，看到 Deepseek 生成的结构化草稿，并可人工确认进入现有工单创建流程。
- white_box: Deepseek adapter、最小知识语料、引用片段、prompt/安全边界、discussion UI、表单集成和测试证据一致。
- anti_cheat: 不允许 AI 绕过人工确认，不允许把 PG/pgvector 或管理员知识库上传混入 MS6，不允许用固定假数据冒充知识检索。

## Developer Decision Boundary

- Deepseek API key、模型选择、计费服务、上线 secret 配置需要用户确认。
- 可先实现 mock/adapter 边界以保护 UI 和 API 合同，但真实 Deepseek 接入前必须明确环境变量和错误处理。
- 若发现知识上下文需求必须依赖持久向量库、管理员上传或 zip 解析，需 handback 或转入 MS7，而不是静默引入 PostgreSQL/pgvector。
