## Purpose

让非专业用户输入模糊需求后，AI 基于项目知识库生成结构化、可审查的工单草稿；AI 只辅助起草，必须由用户人工确认后才写入工单表单或创建工单。本 milestone 不依赖 PostgreSQL/pgvector。

## Completion Signals

1. 产品流定义清楚：输入、输出、人工确认、失败态、权限边界明确。
2. 最小知识库语料来自 repo 内稳定资料和业务结构，不依赖 PG/pgvector。
3. 后端提供受鉴权保护的 AI 草稿接口，输入自然语言，输出结构化草稿。
4. 前端提供 AI 优化需求说明入口，生成结果只填充草稿或表单，不直接创建工单。
5. 安全治理覆盖 prompt 边界、敏感信息提示、错误处理、空知识库 fallback、人工确认约束。
6. API 基础测试、弱输入/正常输入路径、前端手动验收路径通过。

## Acceptance Criteria

1. 用户能输入一段非专业需求并得到结构化工单草稿。
2. 输出至少包含标题、背景、用户故事、验收标准、待确认问题和建议优先级。
3. AI 不直接创建工单，必须人工确认。
4. 不引入 PostgreSQL/pgvector 依赖。
5. 不破坏现有工单创建流程。
6. `npm run lint`、`npm run test`、`npm run build` 通过，或 Gate 记录等价验证理由。

## Milestone Gate Design

- black_box: 用户可从 UI 输入非专业需求，看到结构化草稿，并可人工确认进入现有工单创建流程。
- white_box: AI API、知识库语料、prompt/安全边界、前端表单集成和测试证据一致。
- anti_cheat: 不允许 AI 绕过人工确认，不允许把 PG 迁移混入 MVP，不允许用固定假数据冒充知识库生成。

## Developer Decision Boundary

- OpenAI API key、模型选择、计费服务、上线 secret 配置需要用户确认。
- 可先实现 mock/adapter 边界以保护 UI 和 API 合同，但真实 AI 接入前必须明确环境变量和错误处理。
- 若发现知识库需求必须依赖持久向量库，需 handback，而不是静默引入 PostgreSQL。
